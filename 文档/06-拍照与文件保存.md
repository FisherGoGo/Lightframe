# 06 拍照与文件保存

[返回总览](00-项目总览与开发顺序.md)

Capture 负责一次拍照任务的全过程。先实现单帧保存，再加入多时间采样，不需要一开始就写完整异步导出系统。

阶段安排：C 完成单帧 PNG + JSON 保存，E 完成固定快照、时间采样与分帧进度。目标版本通过内置实验预设复现；从任意导出 JSON 恢复拍摄是加分项，保存元数据本身不等于已经支持回放。

## 1. 需要实现什么

| 功能 | 实现方法 |
|---|---|
| 拍摄快照 | 保存相机、摄影参数、场景配置、时间和种子 |
| 单帧拍照 | 读取 UI 合成前的照片目标 |
| 快门拖影 | 在曝光时间内渲染多个场景状态并平均 |
| 进度与状态 | Idle → Sampling → Finalizing → Saving → Done / Failed |
| 图片保存 | GPU 读回 RGBA8，处理行方向，写 PNG |
| 参数保存 | 用相同文件名主干写 JSON |
| 错误提示 | 路径不可写、读取或编码失败时给出原因 |

## 2. 单帧保存怎么做

第一版直接保存已经生成的 photoColor：绑定它对应的 FBO，设置正确的读附件，调用 `glReadPixels` 读取像素，然后通过图片写入库编码 PNG。

OpenGL 的像素原点在左下，常用图片查看器以左上为原点。选择 CPU 翻转行，或图片写入库的翻转选项，只执行一种。读回时明确设置打包对齐，例如 `GL_PACK_ALIGNMENT = 1`，并确保缓冲大小与实际宽高和通道数匹配。

导出图像已经完成色调映射与显示编码，不能保存时再做 gamma。不要从包含 UI 的窗口 framebuffer 截图，否则参数面板也会被保存。

## 3. 快门多时间采样怎么实现

开始时保存完整 `CaptureSnapshot`：

```text
相机位置与方向、近远裁剪距离
全部摄影参数、照片宽高
场景 ID / 配置、拍摄起始时间 T
样本数 K、随机种子
后处理开关与算法设置
```

首版拍摄期间相机固定，物体按时间运动。样本使用区间中点分布：

```text
sampleTime(i) = T + ((i + 0.5) / K) × shutterSeconds
i = 0 ... K-1
```

每个样本执行：Scene 在 sampleTime 求值 → 用快照相机绘制 HDR 颜色和深度 → 执行景深 → 累加线性颜色。

最后：

```text
averageColor = accumulatedColor / K
→ 应用包含快门因素的曝光倍率
→ 加入一次噪声
→ 色调映射和显示编码
→ 生成照片并保存
```

时间平均描述曝光区间里的平均场景亮度，曝光倍率另外包含快门时长。这种组织不会把快门算两次。增加 K 应主要改善拖影平滑度，而不是让图片越来越亮。

不要先把每个样本变成 PNG 颜色再平均，因为色调映射是非线性的。

## 4. 累加纹理和进度

### Lushfoil 的公开技术参考

开发者公开的长曝光方案也是在曝光期间获取多个图像并合成。他记录了直接求和时出现高值截断、每次简单折半造成后期样本权重过大的问题，最后采用随样本数更新的平均方法，并描述了每秒 30 次采集的实现。[Matt Newell 的长曝光技术文章](https://www.gamedeveloper.com/programming/deep-dive-making-lushfoil-s-long-exposure-photography-system)

本项目采用可控时间采样和线性 HDR 浮点目标，不依赖显示帧率。等权平均可以写成下列递推公式（数学表达是本项目的整理，不是游戏源码）：

```text
A_1 = C_1
A_n = A_(n-1) + (C_n - A_(n-1)) / n
```

该式与全部线性样本求和后除以 K 等价。若未来改用递推平均，仍需使用 A/B 纹理避免同一纹理读写反馈，并且不能在最后再除以 K。当前第一轮继续使用下方的 RGBA32F 求和方案即可。无论选择哪种，快门曝光倍率只在平均之后应用一次。

游戏公开文章没有提供完整渲染管线，不能据此推断其纹理格式、色彩空间或 GPU 调度。本项目的这些约定属于自己的实现设计。

可以采用 A/B 两个浮点累加目标：

```text
清空 A 为零
样本 0：读 A 和当前样本，写 B = A + sample
交换 A/B
样本 1：继续读 A，写 B
...
最终平均 = A / K
```

每轮读写不同纹理，累加 Pass 关闭不需要的混合和深度测试。首版用 RGBA32F 累加，以降低多样本求和溢出和精度问题。

最简单的实现一次拍完整张照片，但样本多时 UI 会停顿。完善版本每个显示帧处理少量样本，显示 `completed / K`；仍在主线程执行 OpenGL，不必引入多线程上下文。

一次完成全部样本只用于初期验证。目标版本按显示帧推进，初始每帧处理 1 个样本，测量后再调整预算。Done / Failed 展示结果后允许再次拍摄；忙碌期间禁止重复启动。最终颜色生成后，先读回像素或保留独立结果纹理，再恢复对共用目标的预览写入。

实时预览和拍照若复用渲染目标，要保证累加纹理独立；每轮先完成拍照样本累加，再渲染预览，避免预览覆盖尚未消费的样本。

K 可先尝试 16、32、64，以运动物体的像素位移决定是否足够。长快门和快运动可能需要更多样本，否则拖影呈离散重影。固定 K 并不能保证任何快门都平滑。

实验默认从 K=32 开始，并保留 K=16/64 对照。先调整运动速度、快门与构图，使正式预设中的相邻时间样本投影位移尽量控制在约 1～2 px；高速、长快门仍有重影时增加 K 或明确记录质量限制，不承诺任意参数组合都平滑。静态场景用于检查改变 K 不改变曝光，运动场景用于检查拖影连续性，两种检查分开进行。

## 5. 文件怎样组织

```text
captures/
  photo_20261012_153000_001.png
  photo_20261012_153000_001.json
```

文件名示例只表示格式。实际使用本地时间、毫秒或递增编号，并检查重名；不要覆盖已有照片。JSON 至少记录：

- 焦距、传感器尺寸、f 值、快门秒数、ISO、对焦距离及单位。
- 相机位置、yaw/pitch、近远裁剪距离。
- 场景 ID、起始时间、种子、样本数、图像尺寸。
- 效果开关、色调映射方式、噪声强度、景深采样和半径限制。
- 配置或算法版本，便于以后判断结果差异。
- 实验预设 ID 与版本、程序版本，以及场景配置和资产标识。

读取文件、资源配置也可能改变场景，因此完整复现还需要保存或引用对应场景配置与资产版本。用 JSON 库序列化，避免手拼字符串造成转义错误。

先写临时文件，确认 PNG 和 JSON 都成功后再完成命名；只有两者都成功才报告保存完成。失败时报告具体路径和原因，并说明是否留下了部分结果。保存后在 UI 显示文件位置。

## 6. 完成条件

- PNG 不含 UI，方向、颜色和 3:2 比例正确。
- 连拍不覆盖，PNG 与 JSON 一一对应。
- 长快门产生更长拖影，等曝光补偿后亮度仍相近。
- 增加 K 改善平滑度，不系统性增加亮度。
- 同一构建、设备与配置下，相同快照与种子能复现结果；不承诺跨显卡逐像素一致。目标版本至少能通过内置预设恢复相同输入。
- 拍照期间修改预览参数不会混入当前照片；拍照结束后能继续操作。
