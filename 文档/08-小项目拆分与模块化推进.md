## 1. 可以怎样拆

可以把整个相机模拟器拆成一组小项目，每个小项目都有一个可以演示的结果，例如“能移动取景”“能调整曝光”“能保存照片”。每次完成一个结果，再接入下一个能力。

建议保留一个仓库、一个 Visual Studio 工程和一个程序入口，用文件模块承载不同职责，用小项目组织开发和验收。这样每次运行都是当前完整版本，上一阶段的功能也能持续检查。

| 拆分方式 | 优点 | 代价 | 本项目的安排 |
|---|---|---|---|
| 按可演示功能拆小项目 | 能持续看到成果，容易判断完成与否 | 一个功能可能涉及多个模块 | 作为推进单位 |
| 按相机、场景、渲染等职责拆代码 | 修改范围清楚，算法容易单独验证 | 单个模块未必能独立演示 | 作为代码组织方式 |
| 每项功能另建工程或仓库 | 适合独立学习实验或独立交付 | 窗口、依赖和着色器容易重复，最终要再次集成 | 有独立用途时再考虑 |

关键是区分“小项目”和“代码模块”：曝光小项目会改参数、着色器和 UI，但这些代码仍分别留在参数、后处理和界面模块中。

现有 01～07 文档继续作为技术说明；本文负责把说明转成具体任务。工程沿用当前 `.slnx`、`.vcxproj`、`Dependencies.props`，暂时没有迁移 CMake 的必要；00、01 已同步当前工程组织。

```text
P00 基线 → P01 骨架 → P02 取景 → P03 焦距
```

这是集成顺序；不表示保存算法依赖景深，也不表示时间动画必须依赖模糊公式。涉及不同功能时可以先验证纯计算部分，最终接入按此顺序进行。截止时间、人数和课程硬性要求尚未确认，因此这里不承诺日历排期。

### P00：确认基线

- 工作：检查现有依赖，构建 x64 Debug/Release，运行当前 `--smoke-test`；手动检查缩放、最小化恢复和 Esc 退出。
- 交付：记录构建配置、命令、结果和一张立方体截图；有失败先处理失败。
- 验收：绘制自检通过，窗口操作正常；其他已有配置的检查按工程交付要求执行。

### P01：整理工程骨架

- 工作：把窗口、初始化和主循环放入 `App`；把立方体顶点及 VAO/VBO 生命周期放入 `Mesh`。保留 Shader 和现有视觉结果。
- 交付：`main.cpp` 负责启动与返回结果；App 协调运行；Mesh 提供立方体创建和绘制能力。
- 验收：原自检仍通过，原错误日志与退出行为可用；GPU 资源在窗口上下文销毁前释放。
- 边界：此项不加入曝光、模型加载或通用资源管理框架。每抽出一部分就构建一次，避免一次搬动所有代码。

### P02：自由取景和简单场景

- 工作：实现 Camera 的位置、方向、观察矩阵、移动、转向和复位；Scene 保存少量物体变换，复用立方体 Mesh。
- 交付：一个有前景主体、地面和远景参照物的场景，可用 WASD 和右键观察。
- 验收：能复位机位；连续移动使用时间差；第一次右键转向不跳动；失焦后不会保持移动。
- 边界：这一轮只组织几何体和实例，正式模型、碰撞与骨骼动画后置。

### P03：焦距和最小参数界面

- 工作：加入 `CameraSettings`，用焦距与传感器尺寸计算投影；接入最小 ImGui 面板和实验 A 复位。
- 交付：固定机位切换 24/35/50/85 mm，窗口保持 3:2 取景比例。
- 验收：变焦不改变机位；窗口缩放不改变摄影构图；UI 操作不会同时触发观察或移动。
- 边界：先显示已生效的参数；暂未实现的景深、拖影和噪声不作为可用效果展示。

### P04：基础光照、离屏渲染和曝光

- 子任务 1：补充法线与基础光照，先验证直接绘制。
- 子任务 2：Renderer 创建 HDR 颜色和可采样深度纹理，原样转显；检查 FBO 完整性、方向与比例。
- 子任务 3：PostProcess 加入相对曝光、固定色调映射和一次显示编码，UI 编辑光圈、快门与 ISO。
- 交付：参数能改变亮度，提供曝光对照及线性亮度读数。
- 验收：快门或 ISO 翻倍，色调映射前亮度约翻倍；等曝光组合亮度相近；UI 不受后处理影响。
- 边界：此时光圈、快门只影响曝光，完整摄影效果由后续项目补齐。

### P05：单帧拍照和元数据

- 工作：复制一次拍摄所需参数，从 UI 合成前的照片目标读回像素，写 PNG 和相同主干名的 JSON。
- 交付：拍照按钮、成功路径与失败提示，文件保存到 `captures/`。
- 验收：PNG 无 UI、方向正确、颜色与照片目标一致；JSON 对应本次输入；连拍不覆盖；两份文件都成功才报告完成。
- 边界：先做单帧读回和保存，不加入线程、PBO 或多时间采样；保存 JSON 暂不等于支持 JSON 回放。

P05 验收后即可整理最低可交付版本，完成相关实验与运行说明；若后续功能未完成，交付时写明范围。

### P06：深度测量和对焦

- 工作：重建正轴向距离；UI 保存取景器实际显示矩形，将点击换算为照片像素；读取深度并更新对焦距离。
- 交付：深度调试图、距离读数与对焦标记。
- 验收：已知距离的物体测量符合预期；留边、UI 和无几何体背景不会误触发；显示缩放后仍能选中对应像素。
- 边界：对焦标记属于 UI，不写进照片；先测距正确，再添加模糊。

### P07：基础景深

- 工作：计算带符号 CoC，验证调试图，再加入圆盘采样和基础跨层权重；接入实验 B。
- 交付：对焦主体和背景的对照，以及等曝光条件下 f/2 与 f/8 的对照。
- 验收：焦平面附近 CoC 接近零；数值例子符合 05 文档；离焦模糊随光圈变化；预览与拍照调用相同算法。
- 边界：记录单层深度的遮挡近似、样本数和最大半径，不让高级边缘改善阻塞后续开发。

### P08：确定性动画和快门拖影

- 子任务 1：Scene 根据指定时间求物体变换，相同时间和配置得到相同结果。
- 子任务 2：Capture 固定机位、参数、场景配置、起始时间及种子，逐时刻渲染，在线性 HDR 中等权平均。
- 子任务 3：拍照按显示帧推进少量样本，显示进度；最终照片读回后再允许共用目标被预览覆盖。
- 交付：实验 C1 的短快门和长快门对照；拍摄期间仍能操作预览。
- 验收：改变样本数不系统性改变静态场景亮度；长快门拖影更长；拍照过程中修改预览不会改变当前快照。
- 边界：OpenGL 调用仍在主线程；噪声留到平均完成后加入。

### P09：简化噪声和实验联调

- 工作：在线性平均结果经过曝光后加入一次噪声；像素、通道与固定种子决定随机值；完成实验 C2 和实验预设复位。
- 交付：静态场景的等曝光 ISO 对照，实验 A/B/C 均能复位、拍摄并保存参数。
- 验收：相同输入和种子可复现；改变时间采样数不会改变噪声设定；各效果可单独关闭；参数说明明确这是视觉近似。

### P10：验收和交付

- 工作：按 [07-界面与验收](07-界面与验收.md) 检查对应交付范围，修复缺陷，记录预览和拍照耗时，整理操作说明及报告。
- 交付：exe、GLFW DLL、着色器及必要资源、使用说明、实验照片和 JSON。
- 验收：从其他工作目录启动仍能找到资源；在实际演示设备运行；记录依赖、资产许可和已知限制。
- 选做：正式模型、阴影、高级景深和高分辨率导出，在目标版本稳定且有时间时另建任务。

## 4. 模块化代码怎么写

### 职责和数据归属

| 模块 / 数据 | 负责什么 | 边界 |
|---|---|---|
| App | 窗口、生命周期、输入分配、每帧调用顺序 | 摄影公式、像素处理和序列化分别交给对应模块 |
| Camera | 机位、方向、view/projection 的计算 | 输入语义由 App 转换，Camera 不依赖 ImGui |
| CameraSettings | 焦距、传感器、光圈、快门、ISO、对焦距离与校验 | App 持有一份可编辑设置；使用者显式接收 |
| Scene | 物体、灯光、场景配置和按时间求值 | 描述场景，不承担绘制和文件保存 |
| Mesh / Shader | 顶点资源与绘制；程序编译、链接和 uniform | 保持小型辅助类，按实际需求添加能力 |
| Renderer | 场景绘制、渲染目标和输出颜色/深度 | 接收明确的场景和相机输入，不读取 UI 控件 |
| PostProcess | 曝光、深度/CoC、景深、噪声和显示转换 | 通过输入/输出目标组织 Pass，不调度拍摄任务 |
| Capture | 固定快照、任务进度、时间采样、读回和保存 | 不直接修改当前可编辑参数 |
| UI | 控件、取景器布局、对焦/拍照/复位请求与结果反馈 | 通过参数和请求与 App 交互，不直接写 PNG |
| ViewportRect / CaptureSnapshot | 显示区域；一次拍摄的固定输入 | 使用普通结构体，仅保存实际需要的字段 |

Renderer 和 PostProcess 的 GPU 输出是受生命周期约束的资源，不应被当作永久图像副本。Capture 若需要延后保存或展示上一张照片，应保留独立结果纹理或已读回像素。

### 模块怎样配合

```text
UI / 键鼠 → App → 当前 Camera、CameraSettings、Scene 配置
                    │
                    ├─ 预览输入 → Renderer → PostProcess → 照片纹理 → UI 展示
                    │
                    └─ 拍照请求 → 复制 CaptureSnapshot → Capture 推进
                                      → 按快照渲染 / 处理 / 累加 → 保存 PNG + JSON
```

允许 Capture 调用 Renderer 和 PostProcess 推进采样；Renderer 与 PostProcess 不反向依赖 Capture。Scene 不持有 App，Camera 不持有 UI，避免模块互相引用形成环。

下面仅示意接口风格，返回类型和错误处理在对应小项目中确定：

```cpp
camera.move(direction, dt);
camera.rotate(deltaYaw, deltaPitch);
auto view = camera.viewMatrix();
auto projection = camera.projectionMatrix(settings);

auto sceneFrame = scene.evaluateAt(sceneTime);
renderer.renderScene(sceneFrame, view, projection);
postProcess.process(/* 输入纹理、设置、输出目标 */);

capture.start(snapshot);
capture.advance(renderer, postProcess, scene);
```

尽量用显式参数传递，避免函数从全局变量里偷偷读取另一份参数。先让简单接口服务当前功能；当 `Capture` 的保存逻辑或后处理 Pass 确实难以维护时，再拆 `PhotoWriter` 或独立效果类。

### 文件结构逐步长出来

P01 已增加 App 和 Mesh，P02 已增加 Camera 和 Scene，后续按小项目补充文件。初期继续使用平铺 `src/`，便于课程项目阅读：

新 `.cpp`、`.h` 要同步登记到 `.vcxproj` 和 `.filters`；新增着色器应接入构建复制规则，保证从 exe 目录加载。先遵循现有大括号换行、中文分段注释和命名习惯。

GPU 资源应由明确的对象拥有并释放。引入拥有 VAO/VBO、FBO 或程序的封装时，明确复制和移动规则，避免默认复制导致重复释放。无论使用显式清理还是析构清理，App 都要保证这些对象在 OpenGL 上下文有效时销毁。

## 5. 每次开发的工作方式

1. **先定义结果**：写明这次打开程序要看到什么、允许改哪些模块、怎样判断通过。
2. **完成最小版本**：先用简单场景和固定参数调通一个能力，再加入可编辑参数和错误提示。
3. **完成必要拆分**：新增算法留在所属模块；已有长函数出现独立职责时再抽函数或文件。
4. **验证并集成**：执行相关构建、自检、数值或视觉检查，复查此前功能。
5. **留下记录**：记录结果、截图/参数、已知问题和下一项任务，再推进下一小项目。

一个小项目如果需要同时解决多个未知问题，就继续拆任务。P04 分成光照、FBO、曝光，P08 分成动画、采样、进度，是为了让每次失败都有更小的排查范围。

| 变更类型 | 适合的检查 |
|---|---|
| App/Mesh 拆分 | 现有绘制自检、窗口操作和资源释放检查 |
| Camera 与参数计算 | 矩阵、复位、单位换算、非法参数边界 |
| 曝光、深度、CoC | 先检查可预期的数值，再观察画面 |
| FBO 与后处理 | 完整性检查、方向/比例、HDR 范围、纹理读写分离 |
| 保存与拍摄状态 | PNG/JSON 对应、重复拍摄、错误路径、快照隔离 |
| 景深、拖影和噪声 | 固定场景、固定输入、对照图与耗时记录 |

纯计算适合小型数值测试；显示效果适合固定输入的截图或读回检查。文档修改和简单文件整理无需为了形式添加测试。当前烟雾测试的橙色阈值用于现有立方体；光照和显示编码引入后，应保留专用基准路径或更新验证目标，不能删除检查来绕过失败。
